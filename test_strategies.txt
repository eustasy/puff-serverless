# Test Strategies for Key Authentication Features

This document outlines test strategies for core authentication features, focusing on what to test for unit and integration tests.

## 1. User Registration with Email Verification

### Unit Tests:
*   **Token Generation (`src/users.js` or utility function):**
    *   Test that `crypto.randomUUID()` is called and returns a value (mock if necessary to check call).
    *   Test that the expiration timestamp for verification tokens is correctly calculated (e.g., 24 hours from now).
*   **Email Validation (if a utility function is used):**
    *   Test various valid and invalid email formats.

### Integration Tests:
*   **Registration Endpoint (e.g., a hypothetical `POST /api/register` calling `user_register`):**
    *   **Success Case:**
        *   Valid user details (name, email, strong password).
        *   Verify that a new user is created in the `users` table.
        *   Verify that a new email record is created in `emails` with `is_verified = 0` and `is_primary = 1`.
        *   Verify that a new password secret is created in `secrets`.
        *   Verify that a verification token is created in `email_verifications` linked to the user and email.
        *   Verify that the console log (simulating email) contains a correctly formatted verification link with the generated token.
    *   **Failure Cases:**
        *   Attempt to register with an email that already exists.
        *   Attempt to register with an invalid email format.
        *   Attempt to register with a weak password (if checked at this stage).
        *   Missing required fields (name, email, password).
*   **Email Verification Endpoint (`GET /api/verify_email`):**
    *   **Success Case:**
        *   Valid, unexpired, unused token.
        *   Verify `emails.is_verified` is set to `1` and `emails.verified_at` is populated for the correct email.
        *   Verify the token is deleted from `email_verifications`.
        *   Verify appropriate success response.
    *   **Failure Cases:**
        *   Invalid token (not found in `email_verifications`).
        *   Expired token (current time > `token_expires_at`).
        *   Attempt to reuse a valid token that was already used (should be deleted, so effectively same as invalid).
        *   Token exists but the associated email was already verified.
        *   Token record exists but the associated email record in `emails` table is missing.

## 2. Login with 2FA

### Unit Tests:
*   **TOTP Generation/Validation (`otplib` usage in `setup_2fa_start.js`, `setup_2fa_verify.js`, `verify_2fa_login.js`, `remove_2fa.js`):**
    *   Test that `authenticator.generateSecret()` is called for new secrets.
    *   Test that `authenticator.keyuri()` is called for QR code generation.
    *   Test that `authenticator.check()` is called with the correct user-provided code and stored secret. Mock `otplib` to verify interactions and control return values for `check()` (true/false) to test logic paths.
*   **Simulated Encryption/Decryption:**
    *   Test that "sim_encrypted::" prefix is correctly added and removed.

### Integration Tests:
*   **User Login (`user_login` function, typically called by `POST /api/login`):**
    *   **Scenario 1: User without 2FA enabled:**
        *   Correct email and password.
        *   Verify session is created in `sessions` table.
        *   Verify session token is returned.
    *   **Scenario 2: User with 2FA enabled:**
        *   Correct email and password.
        *   Verify response indicates `status: "2fa_required"` and includes `user_uuid`.
        *   Verify no session is created at this stage.
    *   **Failure Cases (common to both):**
        *   Incorrect password.
        *   Non-existent email.
        *   Unverified primary email.
*   **2FA Verification During Login (`POST /api/verify_2fa_login`):**
    *   **Success Case:**
        *   Valid `user_uuid` (for whom 2FA is pending after password validation) and valid `totp_code`.
        *   Verify session is created in `sessions` table.
        *   Verify session token is returned.
    *   **Failure Cases:**
        *   Invalid `totp_code`.
        *   Missing `user_uuid` or `totp_code`.
        *   `user_uuid` provided, but 2FA is not enabled for this user (i.e., no record in `secrets` with `secret_type = 'totp_secret'` and `secret_enabled = 1`).
        *   `user_uuid` provided, but no corresponding `secrets` record for `secret_type = 'totp_secret'` exists, or it's not enabled.

## 2.1. 2FA Setup (`POST /api/setup_2fa_start` and `POST /api/setup_2fa_verify`)

### Unit Tests:
*   (Covered by general TOTP unit tests in section 2)

### Integration Tests:
*   **`POST /api/setup_2fa_start`:**
    *   **Success Case:**
        *   User is authenticated.
        *   Verify a new record is created/replaced in `secrets` with:
            *   `user_uuid` matching the authenticated user.
            *   `secret_type = 'totp_secret'`.
            *   `secret_value` containing the "sim_encrypted::" prefixed TOTP key.
            *   `secret_name` containing the generated label (e.g., "YourApp:user@email.com").
            *   `secret_enabled = 0`.
            *   `secret_created_at` and `secret_last_used` are populated.
        *   Verify response includes `qr_code_uri` and `manual_setup_code`.
    *   **Failure Case (2FA Already Enabled):**
        *   User has an existing `totp_secret` in `secrets` with `secret_enabled = 1`.
        *   Verify appropriate error response (e.g., "2FA is already enabled").
*   **`POST /api/setup_2fa_verify`:**
    *   **Success Case:**
        *   User is authenticated and has an unverified `totp_secret` in `secrets` (`secret_enabled = 0`).
        *   Valid `totp_code` provided.
        *   Verify the `secrets` record for `user_uuid` and `secret_type = 'totp_secret'` is updated:
            *   `secret_enabled` is set to `1`.
            *   `secret_last_used` is updated.
        *   Verify success response.
    *   **Failure Cases:**
        *   Invalid `totp_code`.
        *   No prior `totp_secret` setup found in `secrets` for the user.
        *   2FA is already enabled (`secret_enabled = 1`).

## 2.2. 2FA Removal (`POST /api/remove_2fa`)

### Unit Tests:
*   (Covered by general TOTP unit tests in section 2)

### Integration Tests:
*   **`POST /api/remove_2fa`:**
    *   **Success Case:**
        *   User is authenticated and has 2FA enabled (`secrets` record with `secret_type = 'totp_secret'` and `secret_enabled = 1`).
        *   Valid `totp_code` provided.
        *   Verify the `totp_secret` record for the user is deleted from the `secrets` table.
        *   Verify success response.
    *   **Failure Cases:**
        *   Invalid `totp_code`.
        *   2FA is not enabled for the user.
        *   Missing `totp_code`.

## 3. Password Reset

### Unit Tests:
*   **Password Reset Token Generation (`request_password_reset.js`):**
    *   Test that `crypto.randomUUID()` is called for token generation.
    *   Test that the expiration timestamp for reset tokens is correctly calculated (e.g., 1 hour from now).
*   **Password Strength Check (`passwords.js` - `password_check`):**
    *   Test with various strong and weak passwords to ensure criteria are correctly evaluated.

### Integration Tests:
*   **Request Password Reset (`POST /api/request_password_reset`):**
    *   **Success Case (Email Exists):**
        *   Provide an existing user's email.
        *   Verify a token is created in `password_reset_tokens` linked to the correct `user_uuid`.
        *   Verify the console log (simulating email) contains the correct reset link with the token.
        *   Verify a generic success-like response is returned (to prevent email enumeration).
    *   **Case (Email Does Not Exist):**
        *   Provide a non-existent email.
        *   Verify no token is created.
        *   Verify a generic success-like response is returned.
    *   **Failure Cases:**
        *   Invalid email format in request.
*   **Reset Password (`POST /api/reset_password`):**
    *   **Success Case:**
        *   Valid, unexpired, unused `token` and a strong `new_password`.
        *   Verify the user's password in the `secrets` table is updated (new hash and salt).
        *   Verify the `secret_created_at` timestamp is updated.
        *   Verify the token in `password_reset_tokens` is marked as `is_used = 1`.
        *   Verify success response.
    *   **Failure Cases:**
        *   Invalid `token` (not found).
        *   Expired `token`.
        *   Used `token` (`is_used = 1`).
        *   `new_password` is too weak (violates `password_check`).
        *   Missing `token` or `new_password` in request.
        *   Token exists but the associated user_uuid does not have a 'puff_password_sha-384' record in `secrets`.

## General Considerations for All Tests:
*   **Database State:** Ensure tests manage database state appropriately (e.g., setup/teardown, transactions if possible, or specific data seeding per test). For D1, this might involve pre-populating data or cleaning up after tests.
*   **Mocking External Services:** Not applicable here as `otplib` is a library, not an external service call.
*   **Context Object:** Ensure the `context` object (especially `context.env.DATABASE` and `context.request`) is properly mocked or constructed for tests.
*   **Error Handling:** Test for expected error responses, status codes, and error messages for various failure scenarios.
*   **Security:**
    *   Ensure sensitive data (like raw passwords or secrets) is not inadvertently logged or returned in responses beyond what's necessary (e.g., session tokens).
    *   Test for authorization: e.g., User A cannot terminate User B's session.
